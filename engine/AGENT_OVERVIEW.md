## Purpose

Three LangGraph agents support a bank's financial-crime compliance team. All
traces go to one tracing project and are told apart by the `agent` metadata key:

| `agent` metadata | Graph | What it does |
|---|---|---|
| `kyc_onboarding` | `graphs/kyc_graph.py` | Extracts customer documents, screens watchlists, rates risk, and decides APPROVE / REJECT / MANUAL_REVIEW |
| `aml_transaction_monitoring` | `graphs/aml_graph.py` | Analyzes a transaction against customer history, checks sanctions, detects anomalies, raises an alert, and pauses (`interrupt`) for a human reviewer |
| `compliance_summarization_assistant` | `graphs/summarization_assistant.py` | Tool-calling chat assistant analysts use to summarize pending reviews and customer risk |
| `aml_review_actions` | `app/routes/reviews.py` | Analyst approve / reject / escalate actions on AML alerts, with an LLM-written justification and compliance check |

The FastAPI app (`app/routes/`) runs the function-based versions of the KYC and AML agents in `agents/`. They carry the same `agent` metadata as the graphs.

Every trace also carries `revision_id` (git SHA), so compare releases by revision.

## Architecture

- **AML graph nodes:** `normalize_input → analyze_pattern → check_sanctions → detect_anomalies → generate_alert → human_review`
- **KYC graph nodes:** document extraction → watchlist check → risk assessment → decision
- Prompts live in `agents/prompts.py`. Pydantic output schemas (`Alert`, `RiskAssessment`, `KYCDecision`, …) live in `agents/aml_agent.py` and `agents/kyc_agent.py`.
- Reviews persist to SQLite (`app/models_db.py`) via the FastAPI app in `app/`.
- Load is synthetic, generated by `load_generator/`, so customer data contains no real PII.

## What "good" looks like

- **Missed detections are the most severe failure.** A sanctioned-country counterparty (Iran, North Korea, Syria, Cuba; Russia is treated as high-risk), structuring just under the $10,000 reporting threshold, or a transaction far above the customer's history must produce an alert of HIGH or CRITICAL.
- **False positives are a cost, but less severe.** Legitimate payroll, domestic transfers, and amounts in line with history should not be flagged above LOW.
- Severity (LOW / MEDIUM / HIGH / CRITICAL) must be consistent with the 0–100 `risk_score`. A CRITICAL alert with a low score, or the reverse, is a defect.
- Alert `justification` must cite concrete evidence from the transaction (country, amount, frequency). Generic boilerplate is a defect.
- The KYC agent should send to MANUAL_REVIEW rather than APPROVE when source of funds or identity documents are missing.

## Key metrics and feedback keys

- Online evaluation in `evaluation/online_evaluation.py` scores recent triage decisions and sends low-confidence ones to an annotation queue (`needs_review` feedback)
- Offline experiments from `evaluation/run_langsmith_evaluation.py` against the 14-case AML dataset in `evaluation/test_dataset.py`, scored on flag correctness, severity accuracy, indicator detection, and risk score range
- Analyst decisions in the AML Reviews UI. An APPROVE on a HIGH/CRITICAL alert suggests a false positive.
- Latency per transaction. Calls use `gpt-4` at temperature 0.

## Known areas of concern

- Tool call failures in the summarization assistant when the review API is unreachable
- Severity / risk score mismatch in `generate_alert`
- Very long `customer_history` inputs inflating token usage
